# /agents rules (owner: Agents)

Read `NUTRIPLAN_MASTER_SPEC.md` sections 8 and 9 and the `nutriplan-agents` skill first.

## Golden rules

- **Agents decide, argue and explain; math calculates.** An LLM never produces a number shown to the user. Calories, grams, dollars and limits come from `/math` or `/agents/rules/guidelines.json`. Live-mode phrasing is accepted only when `onlyAllowedNumbers()` (in `llm.ts`) confirms every number in the text was handed to the model by code; otherwise the scripted sentence is used.
- **Doctor hard constraints are never relaxed by any code path.** `buildConstraints(profile)` is the only source; the Doctor never concedes. Monitor may make a cap _stricter_ (glucose rising tightens `maxCarbsPerMealG` by 5 g, floor 35 g) and the Doctor keeps the stricter stored value on the next run.
- **Allergies and restrictions are filtered in code**: `filterPool` before optimization, `searchFoods(..., { excludeTags })` when mapping Chef ingredients, and `filterPool` again on the mapped pool.
- **Events**: text under 140 chars (`emitEvent` clamps), 15 to 25 events per run, at least one `objection` and one `concession`, exactly one `decision` and it is last, `tool_call` events carry `data.tool`, the first Doctor proposal carries `data.constraints`, the decision carries `data.planId`.
- **Personalities**: Doctor calm and firm (cites DGA / ADA / DASH / AHA), Chef passionate and playful, Budget practical and funny about money, Monitor observant and encouraging, Orchestrator neutral referee.
- Every agent has a scripted path so the demo works with no API keys. Nothing in `/agents` may throw to the user: the Orchestrator catches everything, emits a failed `decision` (or replays `fallbacks/<alex|maria>-plan-run.json` for demo users on onboarding) and sets the run status.
- Do not edit `rules/guidelines.json`, `rules/engine.ts` or `schemas/index.ts` without the Lead; add new schemas in new files under `schemas/`.

## Plan run protocol (`runPlanNegotiation`)

1. Orchestrator opening. 2. Doctor: `buildConstraints` (saved), rule-group proposals. 3. Chef: base pool from scored templates (instant, no LLM; every slot has at least 4 candidates). 4. Budget prices the pool, objects to the most expensive protein, adds cheaper variants (never removes Chef's meals); Chef concedes. 5. Doctor reviews the pool (code: per meal caps at min servings), Chef replaces removed meals. 6. Column generation: first `optimizePlan` on the base pool (no shadow prices, 2 s limit) -> `buildScarcityBrief` (binding constraints, protein gap, sodium share, cost per slot; all numbers from math) -> Chef answers with 6 new meals (`chef-columns.ts`, Haiku then Gemini, under 10 s; scripted: best templates plus protein-boosted variants) -> Doctor code-checks them -> second `optimizePlan` on base + columns (kept only if feasible and not worse on budget); the orchestrator reports how many columns the solver used. If still infeasible or over budget: Chef (repeats 3, full recipe book), Budget 5%, Budget 10%, max 3 rounds. 7. `verifyPlan` in code; violations reject the plan. 8. Save `MealPlan` (version + 1, `bestEffort` only when over budget but inside every rule), grocery list, Monitor promise, `decision`. Shadow prices run on the critical path only when the second solve was quick and the run is on time; otherwise Budget speaks from `bindingConstraints` and `priceShadowsLater` solves day by day after the decision and writes `shadowPrices` plus refreshed explanations into the saved plan (Why sheet).

## Modes and env

- `AGENTS_MODE=live|scripted` (default live when any key is present). Keys: `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GOOGLE_GENERATIVE_AI_API_KEY`.
- `AGENT_EVENT_DELAY_MS` (minimum gap between events; a slow LLM call or solve absorbs it), `AGENTS_FALLBACK=false` to disable demo replays, `AGENTS_SHADOW_PRICES=false` and `AGENTS_OPT_TIME_SEC` to speed the optimizer, `AGENTS_SHADOW_MAX_MS` (second solve ms under which shadow prices run before the decision; default 3500, `0` always defers), `LLM_TIMEOUT_MS` (overrides every per agent timeout), `CHEF_LLM_BASE_POOL=true` (old behaviour: the LLM invents the whole base pool; slow).

## How to run

- Unit tests: `npx vitest run agents` (vote, orchestrator scripted runs for Alex and Maria, monitor on seeded data).
- Evals: `npm run evals` (`EVAL_USER=priya` for one user, `EVAL_SHADOW_PRICES=true` to include shadow prices). Exit code 1 on any failed check; prints a table.
- Replay a negotiation without the UI: the `replay` skill, or `npx tsx -e` calling `runPlanNegotiation` with a `MemoryStore(null)` via `setStore`.
- Regenerate mocks and fallbacks: `npm run mocks`.
